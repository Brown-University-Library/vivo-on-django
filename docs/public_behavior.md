# Public application behavior

The owner completed the conversion review in October 2026. Preserve the reviewed application's URLs, query meaning, visible content, navigation, and response formats. `config/urls.py` defines registered routes; `vivo_app/views.py` coordinates responses.

## Pages and responses

Paths below are relative to the application's configured browser prefix. IDs, query values, and filenames are placeholders.

Use exact registered routes for suffixes and slash aliases. Keep export routes before the generic individual redirect. An HTTP 200 alone does not establish correct content or download metadata.

VIVO RDF/XML, Turtle, and JSON-LD downloads preserve source bytes and use a separate 60-second cache for successful GET and HEAD requests. Cache hits do not delay expiry, and browser responses use `no-store`. One timeout retries once; another returns a plain-text HTTP 503 asking the visitor to try again in a minute. Handled timeouts log warnings without error email. Missing files and failures are not cached; recognized source failures log warnings without administrator email. See [VIVO downloads](source_journey.md#vivo-downloads) for configuration and freshness.

Public display downloads use filenames based on the requested ID. Both CSV and XML retain Rails' `application/xml` media type; XML is Excel-readable SpreadsheetML. A CSV/XML suffix takes precedence over the query format. Without a suffix, the last repeated `format` value selects the export. GET and HEAD are supported; other methods for these downloads return 405. Missing source records return the existing HTML 404; source, generation, or cache failures return the existing display error page with status 500. An empty organization produces five headings without faculty rows. Unsupported formats do not fall back to CSV. Existing HTML, JSON, and raw-JSON handling retains its existing validation.

Organizations export each distinct member's full faculty record, including update dates and the faculty's own title and organization label. Custom additions and configured teams use existing membership definitions. Member reads use Rails' twenty-record batches and preserve source order within each batch. Missing members are skipped; incomplete or failed source responses stop generation. Public downloads require neither staff attributes nor report definitions. Their server cache shares `REPORT_CACHE_TIMEOUT_SECONDS` with protected reports, defaults to eight hours, and stores both completed formats together under separate public keys. See [public export sources](source_journey.md#public-display-downloads).

Report URLs check the trusted server attribute before reading definitions or cached downloads. Shibboleth handles sign-in and staff eligibility. Report IDs retain Rails' leading-integer interpretation. A suffix takes precedence over the `format` query parameter; only `xml` selects XML, and other values use CSV. GET and HEAD are supported. Unknown IDs return an HTML 404; unusable definitions, source failures, and report-generation failures return an HTML 500. These URLs do not provide report JSON.

Reports keep Rails faculty order, course/research-area sorting, publication sorting, five section headings, text truncation, filename cleanup, and attachment media types. CSV uses LF rows with CRLF between sections and distinguishes null from empty text. XML uses string cells and numeric escapes for non-ASCII characters. The eight-hour default cache serves both formats from the same faculty reads; see [report configuration](source_journey.md#subject-librarian-reports) for freshness and local development settings.

Search accepts `q`, `page`, `rows`, `fq`, and names beginning with `fq_`, matching the Rails search parser. Other search parameter names are dropped and logged without their values. The search continues using the accepted parameters; dropped names do not become Solr query options. As in Rails, `rows` cannot change the fixed 20-result page size. Existing query-value limits and the allowed filter fields still apply. The views handle `format=json` and the facet selector `f_name` separately.

Ordinary `/display/{id}` requests select the person or organization HTML page using the Solr record type, rather than the ID prefix. Configured `team-` IDs retain their separate membership handling. Other nonempty record types, including `UNCATEGORIZED`, return the original VIVO JSON-LD bytes with the backend's successful or not-found status and `application/json` content type. Missing Solr records or records without a type return the HTML 404 page. Failed source reads retain the display error page. Explicit JSON, raw-JSON, CSV, and XML requests keep their existing handlers.

Successful legacy display JSON-LD responses are cached for GET and HEAD using `DISPLAY_JSONLD_CACHE_TIMEOUT_SECONDS` (60 seconds by default; `0` disables caching). Report and CSV/XML download lifetimes remain separate. Browser responses use `no-store` to avoid an additional delay. Cache hits skip both source reads. The fixed lifetime starts after fetching the response, and 404s or failures are not saved. HTML pages remain uncached by this mechanism. See [legacy display JSON-LD](source_journey.md#legacy-display-json-ld) for freshness, source changes, and shared-worker behavior.

A timed-out VIVO display read retries once under the existing generation lock. Persistent timeouts return HTTP 503 with “Page temporarily unavailable,” the search box, and a request to try again in a minute. Handled display timeouts produce log warnings without administrator error email. They remain uncached. Other recognized source failures also log warnings without administrator email. Confirmed missing records return the HTML 404 page for ordinary display and explicit JSON forms; inconsistent or mismatched source results remain errors.

Collaboration CSV requests through `/display/{id}/viz/collab.csv` or `/display/{id}/viz/collab?format=csv` return HTTP 200 with an empty body when the source supplies a valid empty graph. Empty downloads have no header row, matching other graph downloads without connections. JSON retains the source representation and HTML explains that no collaboration data is available. Missing or malformed graph fields and source failures retain HTTP 503 responses.

The homepage uses a nonempty `alias` to redirect to a local search with the alias encoded as search text. Other homepage parameters are ignored. Display requests use `format` to select a representation and ignore other query parameters, including tracking parameters. Ignored parameters are not passed to source readers or included in the legacy JSON-LD cache lookup. They do not change the response format or extend the cache lifetime.

Display CSV/XML suffixes retain precedence over the query format; without a suffix, the last `format` value selects those downloads. JSON suffixes accept an absent or matching query format. Profile JSON accepts repeated matching `format=json` values; raw JSON accepts at most one `format=json_txt` value. On ordinary and JSON display requests, empty, unsupported, or conflicting formats return HTTP 400 before source reads or cache lookup. Explicit formats continue using their own handlers, separate from the ordinary display JSON-LD cache. Django's configured query-field limit remains enforced. These changes apply to homepage and display requests; other endpoint query rules remain unchanged.

Display identifiers must contain 1–80 ASCII letters, digits, underscores, or hyphens. Recognized `.json`, `.json_txt`, `.csv`, and `.xml` suffixes are removed before checking the identifier. Invalid identifiers return the existing 404 response before cache or source reads, including GET and HEAD requests. Identifiers are not trimmed or decoded a second time. Valid identifiers retain normal missing-record and source-failure handling.

Collaboration, coauthor, and coauthor-treemap HTML pages look up their profile before reading graph data. A successful Solr response with zero matches and no documents returns the existing 404 page without a graph request. Failed requests, malformed responses, inconsistent result counts, and mismatched records retain HTTP 503 responses. Existing profiles with valid empty graphs retain HTTP 200 and their explanatory message. Missing-profile responses are not stored in the application cache; the next page request checks Solr again. JSON and CSV graph downloads retain their existing graph-only reads.

Organization HTML pages retain an expected member marked `UNCATEGORIZED` and use the standard person placeholder portrait, even when that member's record includes a thumbnail. The member's name, title, and link still come from the organization record. `PEOPLE` records retain their normal portrait handling. Unexpected or duplicate member IDs, other unsupported record types, and failed source requests remain errors. This fallback applies only to organization-page portrait lookup; other membership and export rules remain unchanged.

Organization publication and research-area charts read all listed members in groups of twenty, including organizations with more than five hundred members. Listed members marked `PEOPLE` or `UNCATEGORIZED` contribute their available publication and research-area data. Missing optional chart fields do not block other members' data; research charts retain these members, while publication charts include only members with countable publications. A listed `UNCATEGORIZED` member with no `json_txt` field remains in the research chart using its available display name, without invented publications or research areas. This exception applies only when the field is absent: a present empty, null, or malformed value remains an error, and `PEOPLE` members still require valid record data. Unexpected or duplicate member IDs, other record types, malformed records, and failed source reads remain errors. A confirmed missing organization returns 404 for HTML, JSON, and publication CSV requests. Successful results share a separate short server cache across a chart's formats, using `CHART_CACHE_TIMEOUT_SECONDS` (60 seconds by default; `0` disables caching). Failures and missing organizations are not cached. Cache hits do not extend the lifetime, and browser responses prevent additional caching. Ordinary profile pages remain unaffected. See [organization charts](source_journey.md#organization-charts).

CV, chart, graph, and VIVO download requests ignore query parameters they do not use, including tracking and translation additions. CV requests retain only the optional `dt` version. Collaboration and coauthor pages retain their existing choice of `format=json`, `format=csv`, or `fit=1`; treemaps accept only the format option. URLs with an explicit download suffix accept an absent `format` parameter or one matching that suffix. Organization chart HTML URLs do not accept a `format` parameter; their JSON and CSV forms use the existing suffix URLs. Ignored additions are neither forwarded to sources nor included in cache keys, and they cannot extend the existing cache lifetimes.

Image and CV delivery, supported chart and graph routes, and individual redirects/downloads accept GET and HEAD; other methods return 405 before cache or source reads. Malformed file paths and record IDs, mismatched download IDs, and unsupported download suffixes return 404. Invalid or repeated CV versions and invalid, repeated, or conflicting chart/download options return 400. These request errors do not generate administrator error email. Source, cache, and document-validation failures retain their separate existing handling, including checks on redirects returned by the document source.

Public image responses accept JPEG, PNG, GIF, and WebP files up to 20,000,000 bytes. CV routes retain their existing `.pdf` URLs and version queries. A successful CV source response must declare `application/pdf` and start with `%PDF-`. Valid PDFs keep their bytes, browser viewing, HEAD lengths, and single-range handling. A file that fails either check returns a friendly HTML 404 page asking the visitor to contact the profile owner. The application logs a warning naming the relative CV filename without sending an administrator error email for the rejected document. Failed validation is not cached, so a corrected PDF can appear on the next request. The document limit remains 10,000,000 bytes. An image or document source 404 returns a local 404, while source connection and service failures retain 503.

Successful images and CV files share the existing server cache and generation locks under separate media keys. `MEDIA_CACHE_TIMEOUT_SECONDS` defaults to 60 seconds; `0` disables media caching. The fixed lifetime starts after a successful fetch, and hits do not extend it. Source addresses, file paths, and document `dt` versions distinguish entries. Redirects, missing files, and failures are not cached. Media responses prevent browser caching from extending this delay. Ordinary profile HTML remains uncached by this mechanism. See [public images and CV files](source_journey.md#public-images-and-cv-files).

## Supporting services and boundaries

The webapp reads existing services. It does not rebuild Manager, provision Solr, or implement VIVO. External destinations remain separate workflows.

Account/editing routes commented out in `config/urls.py` remain disabled. Their code, templates, models, and migrations are retained at the owner's request. The installation's Shibboleth restriction is managed separately; future browser checks use the access already arranged.

## Maintenance

The application reads configured services. Tests provide made-up source responses to the same processing and rendering code. Preserve existing source-error behavior and optional-source fallbacks.

Use [development checks](development_checks.md) for changes and [source configuration](source_journey.md) for settings. [Historical scope](../historical_conversion_info/original_scope/public_endpoint_scope.md) explains selection of the conversion endpoints; old case statuses are not a current backlog.

Administrator error email is reserved for unexpected exceptions from code failures. When the app catches an unexpected exception to show an error page, its original traceback and underlying cause remain in the email and logs. Recognized source, configuration, record-validation, report, and cache failures log warnings without administrator email, even when their response is 500 or 503. Invalid requests retain their existing responses without error email. Django records each handled response once, preventing an additional status-only error email. Existing response contents and timeout retry behavior remain unchanged; production error pages do not expose tracebacks.
