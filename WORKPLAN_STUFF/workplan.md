## Automatic deployment and verification

The application server invokes its existing update caller every minute. Confirm which branch it follows; current releases are on `main`. The minute is the approximate delay until the next attempt starts, not a guarantee that code is already running. Pulling, installing dependencies, static collection, restart, and checks take additional time. The wrapper skips an invocation when the same caller is still running.

About a minute after pushing, check the existing application-relative `/version/` endpoint through permitted access; repeat approximately every thirty seconds with short waits and concise updates. Compare the expected branch and full commit with `response.loaded_version`, captured when application code loads. `response.version` reads the checkout and can advance before restart. Check the changed pages, actual served asset bytes and rendered behavior too. A known later tracking commit may qualify after confirming that it includes the implementation; record its actual loaded revision. Reconcile an unexpected revision before claiming results.

Static collection remains part of every update. When authorized server access exists, retain the collected-file check from the server guide. Without that access, record the command check as not run and use permitted browser delivery evidence; do not claim the command passed. A current asset query string is not proof that collected copies or cached browser resources are current.

The initial limit for an unexplained deployment delay is ten minutes. Adjust and record it if observed successful deployments normally take longer. At that limit, inspect authorized deployment output when available; otherwise record the unknown cause. Keep verification pending, stop further pushes, report the required recovery action, and continue independent local tasks if useful. A skipped invocation, unavailable log, authentication redirect, or browser block is not a passing check.

Before another push, confirm that the preceding release is running and account for every recorded change. An isolated comparison that lacks permitted evidence can remain blocked with a concrete next action while other cases proceed. An unconfirmed or failed deployment stops further pushes; a blocked comparison does not become a pass merely to keep work moving.

The current wrapper runs the full caller even when no new commit exists, so the application may restart during a comparison. Check the loaded revision before and after each comparison group. Retry evidence affected by a changed revision, failed request, interrupted interaction, or unsettled loading; a restart at the same commit can still disrupt a page. Record a blocker if repeated restarts prevent verification. Skipping unchanged deployments would require a separate code change.

## Daily cutoff and resuming work

A daily-start prompt establishes one cutoff: 08:00 `America/New_York` on the calendar day after that prompt is first accepted. Read the clock and save the full local date, timezone and UTC equivalent in `../../ongoing_run.local.md`. A resumption keeps that original cutoff. Midnight, compaction, automatic continuation and recovery must not move it. Only a new explicit daily-start prompt establishes a new date.

Use a persistent Codex Goal when the owner explicitly requests it. Its objective is the bounded daily run, not declaring the entire conversion complete. Carry the cutoff and private checkpoint across turns. Deployment cron only deploys; it does not restart an idle Codex chat. Budget limits, interruptions, unavailable tools or blockers can stop continuation. Save the stopping reason and exact next action instead of claiming completion.

Check the clock before each new pass and replacement URL. At or after the cutoff, freeze the active pass's membership and planned actions. Finish the work already started, required checks, authorized commits/pushes, deployment verification and records. Do not start another pass, refill slots, or extend the active pass indefinitely with new improvements. Carry unresolved work into the handoff. Once the cutoff and active-pass finish conditions are met, complete the daily-run Goal and report pushed/loaded revisions, verified fixes, completed URLs, pending checks, blockers and the next action. The server's cron job continues independently.

The private checkpoint records the run ID, acceptance time, cutoff, branch, writer, pass/start time/planned actions, releases and their local/remote/loaded revisions, evidence references, pending checks, progress-snapshot time and next due boundary, exact next action, and actual stop time/reason. Update it after pushes, deployment confirmation, meaningful verification and pass boundaries. A new workspace must recover it before resuming the same run; if its cutoff is unavailable, do not invent a later one. A replacement chat confirms that the prior writer stopped. Preserve permitted read-only browser access and existing access restrictions.

For another case, check that it uses the same behavior and inputs relevant to the difference. Record-specific document bytes, content, links and variations still need their own checks. 4. **Codex asks for one decision when the required behavior or an intentional difference needs owner judgment.** Record a concise recommendation, affected cases and the exact decision needed. Do not accept the difference on the owner's behalf. Keep independent work moving without repeating the same decision request or failed investigation. Revisit the difference when a fix, owner response, changed source or other new evidence provides a reason.
5. **Codex records one resolution and checks its applicability to each affected case.** Link each case's result to the shared record and its deployed evidence or explicit owner acceptance. Shared resolution alone does not complete a URL with other unfinished checks. Preserve case IDs, check definitions and the completion denominator.

## Compare and decide completion

**Every required URL-pattern endpoint must eventually be confirmed visually against Rails.** This is a completion requirement for each endpoint, not just for one representative page in a family or one implementation batch. Record the endpoint, required variation, page or artifact inspected, comparison state, date, deployed revision, result, and private evidence label. For redirects, data responses, downloads, and assets, visually inspect the relevant destination, displayed response, downloaded document, or consuming page and record how it demonstrates that endpoint. Keep the applicable response and behavior checks as well. A successful status code, matching data, or passing local test does not satisfy visual confirmation by itself.

Use Playwright for rendered pages, controls, navigation, keyboard use, downloads, and matched screenshots. Use `httpx2` for redirects, status, headers, and response formats. Extend the existing [comparison command](../tools/compare_sites.py) and [guide](../docs/conversion/browser_comparison.md) when reusable checks are needed. Use interactive browsing to inspect a difference that existing assertions cannot explain.

Compare Rails and Django close in time. Keep screenshot pairs on the same browser build and environment, with matching viewport, scale, fonts, locale, timezone, and interaction state. Check desktop and narrow layouts and content revealed by scrolling or controls. Follow [visual evidence reuse](../docs/conversion/browser_comparison.md#reuse-visual-evidence) to account for the complete view using new inspection and applicable earlier evidence. When taking complete captures, confirm actual bitmap dimensions and scroll position zero, then continue through the footer. For animated dialogs, verify the intended title and settled active control before recording values. Keep required failed requests visible. Explain random imagery or changing source data separately; do not hide missing content or widen a tolerance merely to pass. If data cannot be aligned, retain valid structural checks and mark exact content as needing review.

Run explicit HTTP requests sequentially, waiting at least 0.3 seconds after each response, including redirect hops. Normal browser assets may load concurrently. Stop and record access challenges or unavailable required services. Save upstream responses only when they help reproduce a particular difference or support a useful offline check. Prepared, replay, and live results remain distinct; missing data must not silently select live access or sample content.

Report each current URL's comparison result, each fix's result, remaining differences, blocked checks, and the next action. Count deployed-verified cases separately from local-only cases. A family is complete only after all of its required variations are covered. Reopen a completed case if a later shared change produces a regression. The owner judges final acceptance and proposed intentional differences.
